# 数据库容量自动刷新与代码审查记录

版本：0.3.1；日期：2026-09-18。源码留在 Git 工作区供用户自行提交，不生成交付压缩包、不自动 commit/push。

## 问题、根因与修复

旧代码在 MySQL 8 直接读取 information_schema.TABLES，未绕过默认 86400 秒统计缓存。昨日新增的 ALLOCATED_SIZE 查询还引入了 PROCESS 权限要求，且不能解决无权限账号的原统计缓存问题。单凭截图无法断言应用账号缺权限；本次不沿用该推断。

新实现直接在同一借出的连接上等待 `SET SESSION information_schema_stats_expiry=0` 成功，再读取当前库所有 BASE TABLE 的 DATA_LENGTH、INDEX_LENGTH、DATA_FREE。只有 ER_UNKNOWN_SYSTEM_VARIABLE 走 MariaDB 兼容路径；权限错误、断线错误均返回失败状态。无需修改 RDS 参数组、数据库结构、授权，不执行 ANALYZE/OPTIMIZE。

三张页面共用 `/api/database-storage`，显示数据容量、索引容量、原始字节数、精确行数和采样时间。后端每进程共享最多 10 秒结果并合并在途查询；浏览器每次请求结束 10 秒后再次查询，避免慢查询时叠加请求。网页写入完成使缓存失效并触发刷新；外部 SQL 写入由下一次轮询采样。失败时保留最后成功结果并显示过期，无结果时明确显示读取失败。

精确行数覆盖八张业务表；容量涵盖当前账号可见的当前库所有基础表。应用账号应具有当前业务库的 SELECT 权限，不能依靠只授予部分表来代表整个库。容量是存储引擎统计估算，空间按页分配；绕过缓存也不保证每写一行容量就增加。引擎后台统计自身可能延迟数秒或更久更新，本次 MariaDB 实测也观察到该现象。系统不通过补造数据或改写统计值制造增长。

参考：https://dev.mysql.com/doc/refman/8.4/en/information-schema-tables-table.html

## 同步代码审查与调整

审查覆盖连接池、事务、认证、路由与输入校验、门店设备关联保护、造数与持续负载、小时汇总、迁移快照比较、启动部署入口；这不等同于正式安全审计或真实腾讯 DTS 验收。

- 修复本地模式只填写 APP_AUTH_USER 或 APP_AUTH_PASSWORD 一项时静默跳过认证：现在启动即提示配置不完整。
- 修复持续负载 STOPPED 后运行时长继续增长。
- 修复已提交造数后，容量查询失败导致整个接口报失败、诱发重复造数的问题。造数结果仍成功，容量结果为 null/unavailable；真实写入失败仍按原逻辑失败。
- 修复 CLI target-mb 接受 5000、底层却只接受 2000 的不一致，避免参数最终被拒绝前先写入种子数据。有效造数规则保持不变。
- 新版示例配置将 APP_VERSION 留空，默认读 package.json，避免新版代码仍显示旧版本。现有 .env 未修改。
- 门店关联删除保护、小时汇总与客流一致性、并发 Marker、事务回滚、跨站写入保护、迁移内容和结构比较已通过原集成测试。

## 本地复查和 Git 提交

在项目目录运行：

```powershell
npm run lint
npm test
$env:ENV_FILE='.env.local'
npm run test:integration
node tests/storage-integration.js
```

MariaDB 本地测试使用 `.env.mariadb-test`，数据库须已启动。专项测试限回环地址并会创建独立测试库；执行账号需有建库和创建临时只读账号的权限。浏览器测试可通过 PLAYWRIGHT_MODULE 和 CHROME_PATH 指定已有安装，不会为项目增加生产依赖。

直接诊断当前配置（只读）：`npm run db:storage` 或 `diagnose-storage.bat --no-pause`。报告中 beforeBytes 是该会话默认缓存查询，fresh.bytes 是同会话绕过缓存后查询；两者相等也可能只是当时缓存已新鲜，不能判定修复无效。

自行提交：

```bash
git status --short
git diff --check
git diff
# 使用 git add -p 检查已有跟踪文件；新文件须显式添加
# 本次新增文件：
git add services/storageService.js public/js/database-storage.js views/partials/databaseStorage.ejs scripts/db-storage-diagnose.js tests/storage.test.js tests/storage-integration.js diagnose-storage.bat docs/容量修复与代码审查说明-20260918.md
git add -p
git diff --cached --stat
git diff --cached
git commit -m "Fix live database storage statistics and reviewed runtime issues"
git push
```

提交前确认旧有未提交改动也符合你的意图。.env、数据库、报告、node_modules 均不应提交。没有新的依赖，不需要为了此改动升级 npm。

## AWS 更新与验收

1. 等当前 Generate/负载批次结束，记录旧提交号 `git rev-parse HEAD`。源码目录执行 `git pull --ff-only`；如果源码与 /opt 运行目录不同，按原流程 `sudo bash deploy/install.sh` 同步到 `/opt/passenger-flow-codex`。保留现有 .env，不执行 seed/generate 初始化旧库。
2. 如 .env 固定 APP_VERSION=v0.3.0，可改为 APP_VERSION=，让版本从源码自动读取。其他连接配置保持现有有效值。
3. 重启应用（无数据库结构迁移）：

```bash
sudo systemctl restart passenger-flow
sudo systemctl status passenger-flow --no-pager
cd /opt/passenger-flow-codex
sudo -u passenger env HOME=/var/lib/passenger PATH=/usr/local/bin:/usr/bin ENV_FILE=/opt/passenger-flow-codex/.env /usr/bin/env node scripts/db-storage-diagnose.js
```

4. 核验报告：status=ok；MySQL 8 的 fresh.cacheMode=bypassed；核对 database 是目标业务库。若 beforeBytes=约0.53MiB 而 fresh.bytes 明显更大，可现场确认缓存问题。报告只保留错误码，不包含密码或完整 DB_HOST。
5. 浏览器强制刷新首页、Migration Lab、Migration Check，新卡片应有 MiB/GiB、字节数、精确行数和采样时间。使用既有或你启动的写入批次，等待轮询确认行数增加、时间更新；容量在引擎分配/更新统计后增长。只填充原有空闲页时容量可能不变。
6. 若仍固定数值，把诊断 JSON（不必提供 .env）交回分析。若引擎返回值本身未更新，不能承诺靠网页轮询消除引擎延迟，也不自动执行重型 ANALYZE/OPTIMIZE。

回退：先结束写入批次并停止应用，将已记录旧提交检出到单独源码目录，按原同步方式覆盖运行代码、保留 .env，重启服务。此修复不改表结构，无需恢复数据库或删除数据。不要对带有未提交工作的目录使用 git reset --hard。
