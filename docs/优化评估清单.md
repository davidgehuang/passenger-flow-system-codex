# 客流系统优化评估清单（只分析，不实施）

> 基线：仓库版本 0.3.2；分析日期：2026-09-23。优先级表示**建议先验证的顺序**，并非已证明的生产故障严重等级。下表区分代码直接确认的行为与需要测量的风险。未连接 AWS、VMware 或腾讯 DTS；历史本地测试不替代线上指标。

## 评估方法与优先级

先固定当前提交号、数据库版本、表行数、数据量与运行方式，再用只读指标或**独立实验库**测量。对每项记录触发场景、耗时／资源、错误率或一致性结果；只有测量超过业务可接受范围，才进入设计与修改。实验数据库可做故障注入，现有业务库只做授权范围内的只读观察。

| 优先级 | 含义 |
|---|---|
| 高 | 可能影响迁移正确性、数据重复或大库稳定性，建议在下一次真实迁移／大规模写入前验证 |
| 中 | 当前实现有边界，是否需要改变取决于使用频率、容量和运维目标 |
| 低 | 可用性、交接或维护成本改进；先确认更高优先级项 |

## 待评估事项

### O01　容量卡片每次采样执行八表精确行数统计〔高；成本待测〕

- **代码确认**：`models/statsModel.js` 的 `collectStorage()` 在容量查询后，对八张业务表执行 `COUNT(*)`；`services/storageService.js` 每进程最多复用 10 秒；三个页面浏览器轮询。`models/flowEventModel.js` 的页面分页也执行计数。
- **触发／影响假设**：`flow_events`、操作审计等表继续增长时，精确计数可能消耗 CPU、I/O、连接池容量，拖慢写入或页面；多应用进程的内存缓存互不共享。现有本机测试只证明功能，不证明百万／千万行与 AWS RDS 负载下的成本。
- **缺失证据**：典型及峰值行数、10 秒内调用量、各计数 SQL 的 p50/p95 耗时、慢查询、RDS CPU／ReadIOPS、连接池排队和与写入并发时的变化。
- **验证及后续方向**：在独立放大库和受控线上时段观察各 SQL；若成本显著，讨论精确数与更新频率的取舍、异步维护计数或手动精确刷新。不得把近似 `TABLE_ROWS` 偷换成“精确行数”。

### O02　完整快照长时间占用一致性只读事务〔高；容量相关〕

- **代码确认**：`services/snapshotService.js` 在一个一致性只读事务内遍历八表全部行，按 1000 行分页读并计算内容摘要，同时获取结构。`scripts/db-snapshot.js` 写出 JSON 报告。
- **触发／影响假设**：大库快照耗时可能较长，InnoDB 需保留旧版本；迁移割接窗口、undo／磁盘和数据库读负载可能受影响。代码尚无针对大库的快照时长上限或分段结果可恢复机制。
- **缺失证据**：实际八表行数、metadata 平均长度、快照耗时、事务与 undo 压力、RDS I/O、割接窗口要求。
- **验证及后续方向**：在真实规模的隔离副本上执行只读快照并记录资源；若超出窗口，再设计分段一致性或数据库原生校验策略，保留全量内容与结构比较的验收语义。

### O03　Migration Lab 分块提交后的重试与对账〔高；行为已确认〕

- **代码确认**：`services/migrationLabService.js` 每块最多 250 条事件单独提交；批次失败记录已提交行数，CLI／网页再次发起操作会建立新批次。`tests/integration.js` 验证块内回滚与汇总一致。
- **触发／影响**：网络断开、应用停止或中途 SQL 错误后，原请求已提交的块仍保留。直接重试 INSERT／Generate 会继续新增，直接重试 UPDATE／DELETE 也可能触及不同或重复记录；操作者必须先核对 `migration_batches.affected_rows`、当前数据与审计样本。
- **缺失证据**：真实中断场景发生率、操作恢复的 RTO、业务是否要求“同请求只执行一次”、现有操作手册被遵循情况。
- **验证及后续方向**：在独立库中于多种块边界故障注入，测算可恢复性；若需要自动恢复，设计操作级请求 ID、持久游标与明确的重放语义。当前审计表只保存样本，不能替代逐行恢复日志。

### O04　持续负载状态仅保存在 Node 进程内〔中；行为已确认〕

- **代码确认**：`services/workloadService.js` 保存单例 `WorkloadEngine`；`services/workloadEngine.js` 用定时器和内存集合管理在途操作；`app.js` 在正常退出时调用 Stop。
- **触发／影响**：进程异常退出或重启会终止调度并丢失原 QPS、比例和本轮内存统计；已落库的数据与批次仍在。多进程／多实例没有统一负载状态与互斥。
- **缺失证据**：是否需要跨重启继续造数、多实例计划、异常退出后的观察／恢复要求。
- **验证及后续方向**：故障注入并核对最后批次和页面状态；若实验需要持续执行，再选择持久任务状态、单工作进程或外部调度，明确人工恢复权限。

### O05　数据库新连接设置时区的完成顺序〔中；风险待证实〕

- **代码确认**：`config/settings.js` 在连接池 `connection` 事件内调用 `conn.query('SET SESSION time_zone = ?')`，没有在可观察的业务查询路径上显式等待其完成；`config/database.js` 可立即借出连接执行 SQL。
- **触发／影响假设**：如果驱动不能保证初始化 SQL 先于该连接上的业务 SQL 完成，首个请求的 `NOW()`、`CURDATE()` 和日期写入可能使用数据库默认时区。**目前没有复现证据，不应写成已发生的时区错误。**
- **缺失证据**：新建连接并发时的会话 `@@time_zone`、首条查询时区、MySQL 8／MariaDB 10.3 驱动行为及配置错误处理结果。
- **验证及后续方向**：独立库反复新建连接，第一条语句同时读 `@@time_zone` 与 `NOW()`，模拟慢初始化及错误；若发现竞态，再将会话初始化放到显式可等待的借出路径。

### O06　批量扩容锁定并读取全部门店设备〔中；规模相关〕

- **代码确认**：`services/baseDataService.js` 预览读取两张表全部列；执行时在一个事务中对全部门店、设备 `FOR UPDATE`，并用数据库命名锁串行化批次，直到事务结束。当前批量工具限制执行后最多 500 家／5000 台。
- **触发／影响假设**：与设备编辑、事件造数并行时可能增加锁等待；以后若扩大工具上限，锁与请求响应时间会增长。既有本地测试覆盖 500／5000，但不是云端网络条件下的并发压测。
- **缺失证据**：实际并发数、锁等待和死锁日志、p95 执行时长、前端／代理超时时间。
- **验证及后续方向**：在独立库同时执行扩容、设备编辑和批量造数，记录等待、失败与回滚；按结果评估缩小锁范围或改用异步批次，仍须保证预览复核与同请求防重。

### O07　不同启动入口的建表行为不一致〔高；配置误用风险已确认〕

- **代码确认**：`scripts/db-ready.js` 受 `AUTO_INIT_SCHEMA` 控制且默认开启；`start-configured.bat` 在此之前**无条件**调用 `npm run db:init`；Linux systemd 的 `ExecStartPre` 走 `db-ready.js`。`db-init` 只补表，不建库、不生成种子。
- **触发／影响**：把面向已有库的 Windows BAT 用于 DTS 目标端，即使设置 `AUTO_INIT_SCHEMA=false`，仍会尝试建表；只读账号则可能启动失败。现有手册要求目标端等 DTS 建表，入口行为需要更醒目的交接提示。
- **缺失证据**：用户实际会用哪个入口启动目标端、目标账号权限，以及是否已有误建表记录；本次不推断曾造成实际迁移故障。
- **验证及后续方向**：用隔离空目标库分别运行各启动入口，核对表创建与退出码；如果目标端也要用 Windows BAT，应单独设计“只读目标启动”入口及显式建表选择。

### O08　实验破坏性操作与单账号访问〔中；产品定位相关〕

- **代码确认**：`middleware/security.js` 使用一个可选 Basic Auth 账号；`routes/migrationRoutes.js` 暴露删除、更新和 Purge；`app.js` 要求云端认证并限定 Node 回环监听。当前没有按角色的授权判定。
- **触发／影响**：有该账号的用户可以执行全部实验操作；如果系统将来供更多业务人员访问，需要限定谁能执行破坏性写入。公网入口的 HTTPS 和网络策略仍须由部署配置保证。
- **缺失证据**：用户群、职责分离要求、访问日志与审计要求、是否从实验转为正式业务系统。
- **验证及后续方向**：先完成权限矩阵和入口威胁评估；确有多人使用时再设计身份提供方、角色授权、操作审批和逐操作审计。此项不表示现有基本保护无效。

### O09　业务关系主要靠应用维持〔中；设计取舍〕

- **代码确认**：`db/schema.sql` 没有外键；`services/managementService.js` 对网页删除做关联检查和锁定。DTS 适配说明明确选择应用层关联。
- **触发／影响假设**：外部 SQL、其他程序或迁移工具若写入不一致关系，应用层检查无法约束；报表可能出现孤儿设备／事件。是否加外键取决于 DTS 兼容和现有数据，不可直接把外键当简单修复。
- **缺失证据**：外部写入来源、孤儿记录数量、DTS 对约束的要求、数据修复成本。
- **验证及后续方向**：定期只读反连接核对，再综合迁移影响选择数据库约束、写入契约或监控告警。

## 决策顺序与下一步证据

建议先围绕 **O07（启动安全边界）→ O03（中断后数据语义）→ O01/O02（大库读负载）** 制定验收阈值，再评估 O04–O09。O05 可通过很小的独立库复现实验尽早确认。每项要记录测量环境、样本量、时间、SQL／日志证据与结论状态；本文件本身不授权代码修改、生产参数调整或数据库写入。
