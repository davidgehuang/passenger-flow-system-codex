版本：0.3.2；日期：2026-09-19。测试为本机 Windows + 独立数据库，未操作 AWS 或现有业务库。

## 已通过

- ESLint；25 项现有单元测试全部通过。
- MySQL 8.0.46、MariaDB 10.3.39：扩容专项 10 组检查通过。
- 空库初始化、旧 5 店/10 设备补到 50 店/200 设备、重复补齐、两次追加、指定门店加设备。
- 4 个并发同 UUID 请求只创建一次；相同 UUID 换参数拒绝；达到工具上限之后仍能重试已提交批次。
- 原有门店/设备字段与状态保持原值；预览后修改资料被拒绝；只读模式禁止写入。
- 真实唯一键冲突和数据库触发器注入故障均整批回滚，门店没有半批残留。
- 真实 CLI 预览/执行/重试、Windows BAT 参数入口通过。
- 真实 Chrome 验证网页预览不写入、追加、指定门店、多次点击保护；拦截已提交请求的响应后，刷新页面重试不重复增加。
- HTTP 认证、跨站拒绝和维护模式测试通过。
- `db:generate` 显式数量作用于旧门店和新门店，不再只作用于新增模拟门店。
- 扩至 500 家/5,000 台后，分页、设备选择、两路并发共 500 条客流成功，客流门店与设备关联一致；新增设备参与客流，设备日志覆盖前 10 台以外设备。
- 两种数据库的原有业务集成测试通过：包括增删改、汇总、回滚、并发 Marker、访问保护、快照比较等。

## 本机耗时样本

| 环境 | 补齐至 500 家／5,000 台 | 两路并发共 500 条客流 |
|---|---:|---:|
| MySQL 8.0.46 | 235 ms | 353 ms |
| MariaDB 10.3.39 | 175 ms | 318 ms |

均为单次本机测试样本，补齐之前约 60 家门店、数百设备，不是从空库创建全部记录的耗时；包含本机数据库和磁盘条件，不能作为 AWS 网络环境的性能保证。

## 容量回归的实际结果

MySQL 容量及真实浏览器自动刷新专项通过。MariaDB 首轮容量专项在 90 秒等待内未观察到引擎容量增加，报告为 FAIL；后续只读查询同一测试库发现 storage_probe 的 DATA_LENGTH 已更新至 9,977,856 字节、近似行数 3,432。未执行 ANALYZE/OPTIMIZE，也未改变数据库参数。

这说明该次统计后来更新了，但不能把首轮失败改写为通过，也不能承诺 MariaDB 的引擎估算容量在每次轮询时即时增长。本次未改动容量查询服务。之后保持程序与数据库配置不变，独立重跑原容量测试通过，包括容量增长、连接池、只读账号、权限恢复及真实浏览器自动刷新。首次失败仍保留，不能以重跑通过证明引擎统计始终能在固定时间内更新。
